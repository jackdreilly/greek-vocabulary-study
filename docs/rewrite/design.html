Greekflash · Rewrite Design

A from-scratch rewrite, in seven decisions.

A reactive, streaming, Firestore-native rebuild — designed so that every AI generation feels immediate and confident, and nothing the AI does is irreversible.

Read time: about 8 minutes. The technical detail lives in docs/rewrite/*.md; this is the human-readable tour.

Vision

The current app works, but it has accumulated friction: hardcoded AI models, modal-driven generation flows, one-shot Firestore reads, a split database, and a deploy process you have to do half-by-hand. The rewrite addresses all of that at once.

Three feelings we're after:

  • Magical immediacy. You click "Generate a course," and you're already on the course page watching it build itself — no spinner, no modal, no waiting screen.
  • Confidence to experiment. Every AI-generated thing carries a lineage tag. If you don't like what the AI did, "revert generation X" wipes exactly those changes and nothing else.
  • Calm. A quieter UI. Fewer counts. One primary action per page. Greek text gets room to breathe.

In and out of scope

In: a hard cutover to a new isolated Firebase project (fanari-b6bb4), new schema, new triggers, new AI orchestration, new admin tooling, new deploy pipeline, new visual design. Content (courses, lessons, vocab, plans, games) is migrated from the old project.

Out: user progress (flashcard SRS, scores, streaks) — explicitly not reimplemented in this phase. Auth and multi-user are deferred but architecturally planned for.

Decision 1

Firestore is the bus.

The client writes a stub. Triggers do the work. The frontend listens.

Today's app has a callable Cloud Function for every AI action — you call it, you wait for it, you get the result back. The new app inverts that:

  1. Frontend writes a placeholder doc directly into Firestore: { status: 'initializing', sourcePrompt }.
  2. Frontend immediately navigates to the page for that doc.
  3. A Firestore trigger picks the doc up, marks it streaming, does the work, writes results back to the same doc (and its children) piece by piece.
  4. The frontend's onSnapshot subscription was already live the whole time. It sees each piece appear.
No more "loading" states. The page is the result, even when the result is half-built. Status indicators are inline and quiet.
More moving parts than a single callable. Triggers need careful locking so two retries don't double-generate. We use Firestore transactions to claim a doc before working on it (lifted directly from fanariotes' proven pattern).
Decision 2

Subcollections match the hierarchy.

Courses → lessons → (entries, plans, games)

Today, everything is flat: courses, themes, entries, lesson_ai_plans, lesson_ai_exercises — all top-level collections linked by foreign-key fields. The new schema mirrors the natural tree:

courses/{courseId}
  lessons/{lessonId}
    entries/{entryId}
    plans/{planId}
    games/{gameId}

Plus a small denormalization: each course doc carries a lessonSummaries map keyed by lesson ID, so the course page renders the lesson list from a single doc read. Triggers keep it in sync.

Listing lessons in a course is now "list a subcollection" or "read one doc with summaries" — no where(courseId == …). Reads are cheaper and reactivity is one subscription per visible tree.
Cross-cutting queries (e.g. "all entries across all lessons matching a search") need collectionGroup indexes. We add those explicitly where needed.
Decision 3

Streaming AI, using Genkit's own primitives.

Small calls, written immediately — orchestrated via Flows, Sessions, Tools, and streaming.

A single 60-second Gemini call that returns a whole lesson worth of content has been the reliability problem with the current app. The new orchestration breaks every generation into a sequence of small, focused calls — and uses Genkit's built-in primitives rather than inventing our own. The four patterns:

  • Flows (ai.defineFlow) — typed orchestration with Zod input/output schemas, automatic tracing in the Genkit Dev UI, and a streamingCallback that lets each intermediate step push progress events.
  • Chat sessions (ai.createSession + chat.send) — for iterative refinement (course title → subtitle → description → lesson outline) where each turn benefits from the prior conversation. Genkit threads message history automatically; we persist it to Firestore so a function cold-start mid-flow can resume.
  • Tools (ai.defineTool) — when the model needs context (existing entries, prior plans, semantically-similar vocab), it calls a tool we've defined. Genkit handles the tool-call loop; the model decides what to look up.
  • Structured streaming (ai.generateStream) — for outputs we want to render as they arrive, like plan widgets.

A plan, for example, becomes a flow that:

01
Opens a chat session, asks for plan metadata and a widget outline. Written to the plan doc immediately.
02
For each widget in the outline, calls generateStream for just that widget. Appended to widgets[] as the schema fills in.
03
Marks the plan ready when the outline is exhausted.
A failed widget retries in isolation. Genkit's tracing lets us debug multi-step flows in a dev UI. We don't reinvent retry/streaming/tool-calling — we use the same idioms Firebase ships in its AI samples.
More API calls per generation, slightly more total latency. The reliability gain, the UX win, and the maintainability win (less custom code) are worth it. Calls are also cheaper per token at the Flash Lite tier.
Decision 4

AI configuration is data, not code.

One Firestore doc, one admin page, no redeploys.

Today, the AI model names are four constants at the top of functions/src/index.ts. Changing one means a function redeploy. The new design:

  • A single doc ai_config/main holds the model choice for each AI "surface" (course gen, lesson gen, plan gen, game scoring, Yiayia chat, Yiayia admin, embeddings).
  • Every Cloud Function reads it before each call, with a 60-second in-memory cache.
  • An /admin/ai page lets you flip a dropdown, save, and within a minute the next call uses the new model.
  • Defaults: every surface starts on gemini-3.1-flash-lite-preview per your rework notes.
Experiments stop costing a deploy each. Production model upgrades become a config change.
Decision 5

Every AI write is traceable. Reverts are atomic.

Generation lineage, end to end.

Every AI generation gets a generationId. Every doc the generation creates carries that ID as a top-level field. A separate generations/{id} doc holds a manifest of every doc the generation touched (creates, updates, array-unions, with enough state to undo each).

Two consequences:

  • Yiayia can revert. A new admin tool, revertGeneration, deletes everything in a generation's manifest in reverse order. The legacy data migration itself is one giant "generation" — if the migration goes wrong, one click rolls back the whole import.
  • "Who made this?" Click any widget or entry, see which generation created it, see the source prompt, see the model used. Forensics built in from day one.
It makes "create immediately, undo if you don't like it" actually safe. Without lineage, "create immediately" is reckless.
Decision 6

A clean backend, a real deploy.

Move to fanari-b6bb4; full GitHub Actions deploys.

The current app shares didibros-6d3ed with the fanariotes lyrics site, which is why the deploy command has to allowlist specific function names — otherwise Firebase CLI offers to delete the "other app's" functions. The new project is isolated to greekflash. No more dual deploy.

The new GitHub Actions workflow runs on every push to main and deploys hosting, functions, Firestore rules, indexes, and storage rules in one go. You will need to do a small one-time setup (service account JSON + a few IAM roles + setting the Gemini API key as a Firebase secret); I'll walk you through it.

Decision 7

A quieter UI — one job per page.

Navigation, drawers, and focused routes carry the load — not crammed pages.

The current UI puts everything on one page: totals stripes, course grid, generate form, chat widget, all stacked. The rewrite goes the opposite way — each page does one thing well, with navigation and drawers carrying secondary concerns.

The patterns:

  • Routes for sections. The four lesson tabs (vocab / cards / games / plans) become four real routes, not query params or in-page tabs that hide content. Same for plans — clicking a plan navigates to /plans/{pid}, a dedicated focus-mode reader.
  • Drawers for secondary actions. "Create a course" and "Add a lesson" forms live in a right-side drawer (bottom sheet on mobile), addressable as /new for deep links. Yiayia is always a drawer, never inline. Streaming status detail is a drawer triggered from the inline indicator.
  • Focus mode. When you're reading a plan or studying flashcards, the top chrome fades to a thin breadcrumb. The content is the page.
  • Modals only for destructive confirms. "Revert this generation" gets a modal. Nothing else does.
  • Counts surface only where decisions happen. No stat stripes. No badge counts on tabs. The status pill on a lesson row tells you what you need to know.

Container types — every visible surface is one of: Page, List page, Reader (focus mode), Drawer, Bottom sheet, Modal, or Inline indicator. Anything new requires a doc-level decision.

Walkthrough: generating a new course

End-to-end, what the rewrite makes possible:

01
You type "Greek for ordering food in a taverna" into the home page field and hit Generate. The frontend writes courses/taverna-greek with status: 'initializing', then immediately navigates to /course/taverna-greek.
02
The course page is already subscribed via onSnapshot. It renders the page shell with a streaming indicator: "Drafting course title…"
03
The onCourseWritten trigger has fired. It claims the doc via a transaction, makes a small Gemini call for course meta, writes title + subtitle + description back. You see the page populate.
04
A second call asks for a lesson outline. The trigger writes 10 lesson stubs as status: 'initializing' docs in the lessons subcollection. You see 10 lesson rows appear, each with an "initializing" pill.
05
Each lesson stub triggers onLessonWritten independently. They generate vocab, an overview, and games in parallel. You see lesson rows flip to "generating," then "ready," over the next few minutes.
06
You click a lesson that's still streaming. The lesson page subscribes; you watch entries appear one by one in the vocab tab.
07
You don't love the overall course. You open Yiayia and say "revert that course generation." Yiayia previews the manifest (1 course + 10 lessons + ~1500 entries + ~250 games + 10 plans) and asks you to confirm. You confirm. Everything is gone — atomically, traceably, with no orphans.

Future trajectory (designed for, not yet built)

You mentioned the app will eventually launch to ~100 users and scale to multi-school. The current decisions don't preclude any of that:

  • 100 users at launch: the schema and triggers as designed handle this without changes. Firestore at this scale is essentially free.
  • Multi-school: school-private content can live under schools/{schoolId}/courses/... with identical document shapes. Global/curated content stays at the top-level courses/ and is visible to all schools. Code that reads a course works for both via a coursePath() helper from day one.
  • Roles:

Admin

Full control. AI config. Generation lineage management. CRUD across all schools. Yiayia admin tools.

Teacher

Within their school: create/edit courses, trigger AI generation, view their students' progress, manage class roster. No AI config control.

Student

Within their school: read content, do exercises, accumulate progress. Can ask Yiayia tutor questions, no admin tools.

None of this is implemented in this phase. But the schema, the generations tracking, and the Yiayia admin gate are all written with a "this becomes a role check later" comment in the right places.
